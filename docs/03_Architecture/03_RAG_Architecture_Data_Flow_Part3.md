# 1. Назначение документа

Настоящий документ завершает описание архитектуры RAG и посвящен этапам формирования запроса к LLM, генерации ответа, причинам возникновения галлюцинаций и связи архитектурных концепций с практической реализацией в Dify.

После изучения всех трех частей читатель должен понимать полный жизненный цикл пользовательского запроса: от загрузки документа в Knowledge Base до формирования финального ответа.

---

# 2. Полный жизненный цикл запроса

Объединим все ранее рассмотренные этапы в единую схему.

```javascript
                Загрузка документа

                       │

                       ▼

               Ingestion Pipeline

                       │

                       ▼

                  Chunking

                       │

                       ▼

                 Embeddings

                       │

                       ▼

              Knowledge Base

══════════════════════════════════════════

              Пользовательский вопрос

                       │

                       ▼

          Embedding пользовательского вопроса

                       │

                       ▼

             Similarity Search (Top-K)

                       │

                       ▼

         Найденные фрагменты документов

                       │

                       ▼

              Prompt Assembly

                       │

                       ▼

                     LLM

                       │

                       ▼

              Ответ пользователю
```

# 3. Prompt Assembly

Это один из самых важных этапов работы RAG.

LLM никогда не получает только вопрос пользователя.

Перед отправкой запроса система собирает единый Prompt из нескольких частей.

Общий принцип выглядит следующим образом:

```javascript
System Prompt

+

Retrieved Context

+

Conversation History

+

User Question

↓

LLM
```

Каждый элемент выполняет собственную функцию.

---

# 4. System Prompt

System Prompt определяет поведение AI.

В проекте он содержит такие правила:

- отвечать только по корпоративным документам;
- не придумывать информацию;
- сообщать об отсутствии данных;
- соблюдать деловой стиль общения;
- не отвечать на вопросы вне области компетенции.

System Prompt является постоянной частью каждого запроса.

---

# 5. Retrieved Context

Это фрагменты документов, найденные системой Retrieval.

Например:

```javascript
Документ:

Reglament_Komandirovki.pdf

Раздел 2.2

Лимит гостиницы:

150 USD
```

Именно этот текст становится источником знаний для модели.

---

# 6. Conversation History

Для сохранения контекста диалога система может добавлять предыдущие сообщения пользователя и ответы AI.

Пример:

```javascript
Пользователь:

Какие суточные?

AI:

1500 рублей.

Пользователь:

А для зарубежной поездки?
```

Без истории диалога второй вопрос был бы неоднозначным.

---

# 7. User Question

Последняя часть Prompt — текущий вопрос пользователя.

Например:

```javascript
Можно ли забронировать гостиницу дороже установленного лимита?
```

---

# 8. Что получает LLM

Для модели итоговый Prompt может выглядеть следующим образом:

```javascript
System Prompt

──────────────

Ты корпоративный AI-ассистент...

──────────────

Context

2.2

Лимит гостиницы

150 USD

──────────────

History

...

──────────────

Question

Можно ли превысить лимит?
```

Важно понимать:

> LLM не знает, где заканчивается Prompt и начинается RAG. Для нее это единый текстовый запрос.

---

# 9. Generation

После получения Prompt начинается генерация ответа.

LLM:

- анализирует вопрос;
- учитывает System Prompt;
- использует найденный контекст;
- формирует ответ на естественном языке.

На этом этапе модель уже не обращается к базе знаний повторно.

Все необходимые данные должны быть переданы заранее.

---

# 10. Почему возникают галлюцинации

Несмотря на использование RAG, языковая модель может генерировать недостоверные ответы.

Основные причины:

### Недостаточный контекст

Система нашла нерелевантный Chunk.

---

### Некорректный Prompt

System Prompt не запрещает модели делать предположения.

---

### Ошибки в документах

Knowledge Base содержит устаревшие или противоречивые сведения.

---

### Недостаточное количество найденных Chunk'ов

В контекст попала только часть необходимой информации.

---

### Ограничения самой модели

Даже при наличии контекста модель может неверно интерпретировать информацию.

---

# 11. Как минимизировать галлюцинации

В проекте используются несколько уровней защиты.

## 1. Качественные документы

Knowledge Base должна содержать актуальные и проверенные регламенты.

---

## 2. Правильный Chunking

Логически завершенные Chunk'и снижают риск потери контекста.

---

## 3. Настройка Retrieval

Необходимо подобрать оптимальное значение Top-K и стратегию поиска.

---

## 4. Жесткий System Prompt

Например:

> Если информация отсутствует в предоставленном контексте, сообщи об этом и не делай предположений.

---

## 5. Guardrails

На следующих этапах проекта будут реализованы дополнительные механизмы контроля поведения модели.

---

# 12. Связь архитектуры с Dify

Все архитектурные этапы имеют соответствие в платформе Dify.

| Архитектурный этап | Реализация в Dify |
|----|----|
| Knowledge Base | Knowledge |
| Ingestion Pipeline | Автоматическая обработка при загрузке |
| Chunking | Index Settings |
| Embeddings | Embedding Model |
| Retrieval | Retrieval Settings |
| Prompt Assembly | Workflow + System Prompt |
| Conversation History | Memory |
| LLM | Model Provider (Gemini 3.6 Flash) |

Это означает, что при настройке Dify мы будем управлять уже известными архитектурными компонентами.

# 13. Архитектурные решения (ADR)

## ADR-014. Формировать единый Prompt перед обращением к LLM

**Решение:**
Все необходимые данные объединяются до вызова модели.

**Причина:**
LLM должна получать полный контекст одним запросом.

---

## ADR-015. Использовать историю диалога

**Решение:**
Сохранять контекст предыдущих сообщений.

**Причина:**
Повышение качества ответов в многошаговых сценариях.

---

## ADR-016. Ограничить генерацию корпоративным контекстом

**Решение:**
Ответы строятся только на основании найденных документов.

**Причина:**
Снижение риска генерации недостоверной информации.

---

## ADR-017. Использовать многоуровневую защиту от галлюцинаций

**Решение:**
Комбинировать Retrieval, System Prompt и Guardrails.

**Причина:**
Ни один механизм по отдельности не гарантирует отсутствие ошибок.

---

# 14. Ограничения MVP

На первом этапе система:

- не использует Hybrid Search;
- не применяет Re-ranking;
- не использует Knowledge Graph;
- не поддерживает Agentic RAG;
- не выполняет автоматическую проверку качества найденного контекста.

Эти возможности могут быть реализованы в последующих версиях проекта.
