# 1. Назначение документа

Настоящий документ описывает архитектурные основы технологии **Retrieval-Augmented Generation (RAG)**, используемой в проекте **Enterprise Knowledge Assistant**.

Цель документа — объяснить, каким образом система получает знания из корпоративных документов, почему она не требует переобучения модели при обновлении информации и как обеспечивается генерация ответов на основе актуального корпоративного контекста.

Данный документ является первым из трех документов серии **RAG Architecture & Data Flow** и посвящен концепции RAG и общей архитектуре решения.

---

# 2. Что такое RAG

**Retrieval-Augmented Generation (RAG)** — это архитектурный подход, при котором языковая модель (LLM) формирует ответ не только на основе своих внутренних знаний, но и на основе дополнительного контекста, извлеченного из внешнего источника данных.

В проекте таким источником являются корпоративные документы:

- регламенты командировок;
- регламенты закупок;
- внутренние политики;
- инструкции компании.

Именно эти документы являются источником истины, а не знания, встроенные в модель.

---

# 3. Почему одного LLM недостаточно

Большие языковые модели обладают широкими знаниями, однако для корпоративных систем этого недостаточно.

Основные ограничения LLM:

- модель не знает внутренних регламентов конкретной компании;
- знания модели могут быть устаревшими;
- модель может генерировать правдоподобные, но неверные ответы (галлюцинации);
- обновление корпоративных правил потребовало бы повторного обучения модели, что практически невозможно.

Поэтому архитектура корпоративных AI-систем строится по принципу:

> **Документы хранятся отдельно, а модель получает только нужный фрагмент информации во время обработки запроса.**

---

# 4. Архитектурная идея RAG

Основная идея RAG заключается в разделении ответственности между двумя компонентами:

| Компонент | Ответственность |
|----|----|
| Knowledge Base | Хранение корпоративных знаний |
| LLM | Анализ вопроса и генерация ответа |

Таким образом:

- корпоративные знания не находятся внутри модели;
- модель не является владельцем информации;
- актуальность данных обеспечивается обновлением документов, а не переобучением модели.

---

# 5. Общая архитектура RAG

На концептуальном уровне поток обработки выглядит следующим образом:

```javascript
Корпоративный документ

↓

Обработка документа (Ingestion)

↓

Разбиение на фрагменты (Chunking)

↓

Создание Embeddings

↓

Индексация в Knowledge Base

──────────────────────────────────────────

Пользователь задает вопрос

↓

Поиск релевантных фрагментов

↓

Формирование контекста

↓

System Prompt

+

Контекст

+

Вопрос пользователя

↓

LLM

↓

Ответ пользователю
```

Эта схема станет основой всей дальнейшей реализации.

# 6. Основные архитектурные компоненты

## 6.1 Knowledge Source

Источник корпоративных знаний.

В рамках MVP:

- Reglament_Komandirovki.pdf
- Reglament_Zakupok.pdf

В будущем:

- инструкции;
- политики;
- стандарты;
- производственные документы.

---

## 6.2 Ingestion Pipeline

Компонент отвечает за подготовку документов.

Основные задачи:

- чтение документа;
- извлечение текста;
- очистка;
- подготовка к индексации.

На этом этапе модель еще ничего не "понимает". Документ только подготавливается для поиска.

---

## 6.3 Knowledge Base

Хранилище обработанных знаний.

После индексации документы становятся доступны для поиска по смыслу, а не только по ключевым словам.

---

## 6.4 Retrieval Engine

Компонент поиска.

Получает пользовательский запрос и определяет, какие части документов наиболее релевантны.

Именно этот компонент является "мостом" между корпоративными знаниями и языковой моделью.

---

## 6.5 Large Language Model

LLM получает:

- System Prompt;
- найденные фрагменты документов;
- вопрос пользователя.

После чего формирует ответ.

Важно понимать:

> **LLM не ищет документы самостоятельно. Она работает только с уже подготовленным контекстом.**

---

# 7. Поток обработки запроса

Ниже приведен общий сценарий обработки пользовательского запроса.

```javascript
1. Пользователь задает вопрос

↓

2. AI получает запрос

↓

3. Выполняется поиск в Knowledge Base

↓

4. Находятся наиболее подходящие фрагменты документов

↓

5. Формируется единый контекст

↓

6. Контекст объединяется с System Prompt

↓

7. Контекст передается в LLM

↓

8. LLM формирует ответ

↓

9. Пользователь получает ответ
```

Данный поток будет детально рассмотрен в следующих частях документа.

---

# 9. Почему RAG подходит для корпоративных систем

Использование RAG позволяет:

- обновлять документы без изменения модели;
- быстро добавлять новые области знаний;
- снизить вероятность галлюцинаций;
- обеспечить единый источник корпоративной информации;
- масштабировать систему без переобучения LLM.

Именно поэтому большинство современных корпоративных AI-ассистентов строятся на архитектуре RAG.

# 10. Архитектурные решения (ADR)

## ADR-007. Корпоративные знания хранятся отдельно от модели

**Решение:**
Использовать Knowledge Base как единый источник корпоративных знаний.

**Причина:**
Обновление информации должно происходить через изменение документов, а не через обучение модели.

---

## ADR-008. LLM не имеет прямого доступа к документам

**Решение:**
Передавать модели только найденные релевантные фрагменты.

**Причина:**
Это уменьшает объем передаваемого контекста, повышает производительность и снижает стоимость обработки запросов.

---

## ADR-009. Поиск выполняется до генерации ответа

**Решение:**
Сначала выполняется Retrieval, затем Generation.

**Причина:**
Ответ должен строиться на основании корпоративных документов, а не внутренних знаний модели.

---

# 11. Ограничения текущей архитектуры

На данном этапе система:

- не использует Tool Calling;
- не обращается к корпоративным API;
- не изменяет данные в информационных системах;
- не учитывает права доступа пользователей к документам;
- не выполняет семантическую фильтрацию по ролям.

Эти возможности будут реализованы на следующих этапах развития проекта.
