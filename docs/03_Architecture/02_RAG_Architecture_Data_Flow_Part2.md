# 1. Назначение документа

Настоящий документ описывает внутренний процесс подготовки корпоративных документов к поиску и механизм извлечения релевантной информации в архитектуре Retrieval-Augmented Generation (RAG).

Цель документа — показать, каким образом обычный PDF-документ превращается в структуру, пригодную для быстрого семантического поиска.

---

# 2. Общая схема обработки документа

После загрузки документа в систему происходит не простое сохранение файла, а последовательность специализированных этапов обработки.

```javascript
PDF / DOCX / TXT / MD

        │

        ▼

Извлечение текста

        │

        ▼

Очистка и нормализация

        │

        ▼

Разбиение на Chunk'и

        │

        ▼

Создание Embeddings

        │

        ▼

Индексация

        │

        ▼

Knowledge Base готова
```

После этого документ становится доступным для поиска по смыслу.

---

# 3. Ingestion Pipeline

## Назначение

Ingestion Pipeline — это процесс подготовки документа к использованию системой RAG.

Важно понимать:

> На данном этапе LLM еще не участвует.

Обработка полностью выполняется системой индексации.

---

## Основные этапы

### 1. Загрузка документа

Пользователь загружает документ.

В проекте:

- Reglament_Komandirovki.pdf
- Reglament_Zakupok.pdf

---

### 2. Извлечение текста

Система извлекает текстовое содержимое документа.

Например:

```javascript
2.2 Гостиница:
Лимит составляет
7000 рублей
для РФ
150 USD
для зарубежных командировок.
```

Если документ является изображением (скан без текстового слоя), потребуется OCR. В рамках MVP мы будем использовать документы с корректным текстовым слоем.

---

### 3. Очистка текста

Перед индексацией удаляются элементы, не несущие смысловой нагрузки:

- лишние переносы строк;
- повторяющиеся пробелы;
- служебные символы;
- колонтитулы и номера страниц (если возможно).

После очистки текст становится более пригодным для дальнейшей обработки.

---

# 4. Chunking

## Что такое Chunk

Chunk — это небольшой логически завершенный фрагмент документа.

Именно такие фрагменты участвуют в поиске.

LLM никогда не работает со всем документом целиком.

---

## Почему нельзя использовать весь PDF

Предположим, документ содержит 80 страниц.

Если передавать весь документ модели:

- возрастет стоимость обработки;
- увеличится время ответа;
- часть информации может не поместиться в контекстное окно;
- снизится качество ответа.

Поэтому документ разбивается на небольшие части.

---

# 5. Пример Chunking

Исходный документ:

```javascript
2.2 Гостиница

Лимит составляет
7000 рублей
для РФ

150 USD
для зарубежных командировок.

2.3 Суточные

1500 рублей...
```

После разбиения:

```javascript
Chunk 15

2.2 Гостиница

7000 рублей

150 USD
```

```javascript
Chunk 16

2.3 Суточные

1500 рублей

50 USD
```

Поиск будет происходить именно по этим блокам.

---

# 6. Размер Chunk

Это один из важнейших параметров RAG.

Слишком маленький Chunk:

```javascript
150 USD
```

Проблема:

теряется контекст.

---

Слишком большой Chunk:

```javascript
Раздел 2

+
Раздел 3

+
Раздел 4

+
Раздел 5
```

Проблема:

поиск становится менее точным.

---

Для MVP проекта выбираем:

| Параметр | Значение |
|----|----|
| Chunk Size | \~500 токенов |
| Overlap | \~50 токенов |

Это хороший компромисс между полнотой контекста и точностью поиска.

---

# 7. Overlap

Chunk'и обычно частично перекрываются.

Например:

```javascript
Chunk 10

...

Командировка
в США

Лимит

150 USD
```

```javascript
Chunk 11

150 USD

Суточные

50 USD
```

Значение **150 USD** присутствует в обоих Chunk'ах.

Это уменьшает вероятность потери важной информации на границе фрагментов.

---

# 8. Embeddings

Теперь начинается самый интересный этап.

После разбиения текста каждый Chunk преобразуется в числовое представление.

Это называется **Embedding**.

Важно:

Embedding — это не перевод текста в другой формат.

Это математическое представление смысла текста.

---

Например

Текст:

```javascript
Лимит гостиницы
150 USD
```

После создания Embedding получится большой вектор.

Условно:

```javascript
[0.23

-0.54

0.77

...

0.11]
```

На практике такой вектор может содержать сотни или тысячи чисел.

---

# 9. Зачем нужны Embeddings

Главная задача Embedding — расположить похожие по смыслу тексты рядом друг с другом в многомерном пространстве.

Например:

```javascript
Лимит гостиницы

↓

Отель

↓

Командировка
```

окажутся значительно ближе друг к другу, чем

```javascript
Закупка

↓

Поставщик

↓

Тендер
```

Хотя ни одно слово может не совпадать полностью.

Именно благодаря этому поиск становится семантическим.

---

# 10. Индексация

После создания Embeddings система строит индекс.

Можно представить его как специальный каталог, позволяющий быстро находить наиболее похожие фрагменты.

Без индекса поиск по тысячам документов был бы слишком медленным.

---

# 11. Retrieval

Теперь рассмотрим, что происходит при вопросе пользователя.

Пользователь спрашивает:

> Какой лимит гостиницы при зарубежной командировке?

---

Система выполняет следующие действия.

### Шаг 1

Создает Embedding вопроса.

---

### Шаг 2

Сравнивает его со всеми Embeddings документов.

---

### Шаг 3

Находит наиболее похожие Chunk'и.

Например:

```javascript
Chunk 15

Score 0.94
```

```javascript
Chunk 16

Score 0.82
```

```javascript
Chunk 9

Score 0.60
```

---

### Шаг 4

Возвращает Top-K результатов.

Для проекта:`Top-K = 3`

---

# 12. Similarity Search

Поиск выполняется не по словам, а по степени смысловой близости.

Наиболее распространенная метрика:

**Cosine Similarity.**

Принцип работы можно представить так:

```javascript
Вопрос

        ↘

      Похожий смысл

        ↗

Chunk
```

Чем ближе направления векторов, тем выше вероятность, что найденный фрагмент отвечает на вопрос пользователя.

---

# 13. Почему Retrieval выполняется до LLM

Очень важный архитектурный принцип.

LLM не просматривает всю базу знаний.

Она получает только уже найденные фрагменты.

Последовательность выглядит так:

```javascript
User

↓

Retrieval

↓

Top-3 Chunk

↓

LLM

↓

Answer
```

Это позволяет:

- сократить стоимость обработки;
- ускорить генерацию;
- повысить релевантность ответа.

---

# 14. Как это реализовано в Dify

При загрузке документа в Dify большая часть описанных процессов выполняется автоматически.

Однако архитектор должен понимать, какие этапы скрыты за интерфейсом платформы.

| Архитектурный этап | Реализация в Dify |
|----|----|
| Загрузка документа | Upload File |
| Извлечение текста | Parser |
| Chunking | Index Settings |
| Overlap | Index Settings |
| Embeddings | Embedding Model |
| Индексация | Knowledge Base |
| Retrieval | Retrieval Settings |

Именно поэтому настройка параметров Knowledge Base напрямую влияет на качество ответов AI.

# 15. Архитектурные решения (ADR)

## ADR-010. Использовать Chunking вместо передачи полного документа

**Решение:**
Разбивать документы на небольшие логические фрагменты.

**Причина:**
Повышение точности поиска и снижение объема передаваемого контекста.

---

## ADR-011. Использовать семантический поиск

**Решение:**
Применять Embeddings и Similarity Search.

**Причина:**
Поиск должен учитывать смысл запроса, а не только совпадение слов.

---

## ADR-012. Использовать Overlap между Chunk'ами

**Решение:**
Добавить пересечение соседних фрагментов.

**Причина:**
Снижение вероятности потери информации на границах Chunk'ов.

---

## ADR-013. Использовать Top-K Retrieval

**Решение:**
Передавать в LLM несколько наиболее релевантных Chunk'ов.

**Причина:**
Повышение полноты контекста без значительного увеличения объема запроса.
